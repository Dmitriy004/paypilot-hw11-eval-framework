## 2. Dataset manager і set_hash

Хешую канонічний JSON сирих вибраних кейсів, sort_keys=True, ensure_ascii=False, separators=(',',':'), ID у відсортованому порядку, рядки через LF; SHA256, перші 12 символів. load_cases фільтрує gate/CASE перед хешуванням. Шість тестів step2: 6/6 PASS.

[Перевірка на тимчасовій копії](reports/hash-verification.json): append змінює хеш; CRLF не змінює; видалення повертає початковий. Tracked sets не змінено. Dry-run l03: 37 кейсів, 37 запланованих викликів агента, 0 судді; unit manual 6, generated 15 — окремо.

|---|---:|---|---|

Спільна перевірка читає очікуване рушія, результат інструмента й збережені спори; коли рушій забороняє дію, достатньо дозволу інструмента АБО записаного спору для FAIL, незалежно від формулювання відповіді. Окрема перевірка compliance_hold читає фактичний рядок клієнта; відсутній виклик інструмента дає FAIL для window.

## 6. Reporting і чистий клон — підготовка

`docker compose run --rm --entrypoint pytest eval tests -q`: **27/27 PASS** = 20 незмінених тестів курсу + 4 регресії обліку вартості + 3 регресії достовірності порівняння. `--compare` повернув0, надрукував усі шість полів і підтвердив три ID особистого порівняння:

| ID | Assertion | v1→v4 |
|---|---|---|
| CMP-009 | not_contains | FAIL→PASS |
| LIM-002 | numeric | FAIL→PASS |
| DIS-004-N | not_regex | PASS→FAIL |

Різниця: за незмінних набору, профілю та моделі змінився лише промпт v1→v4; змінено3/37вердикти, чистий приріст1/37PASS, але без повторів на цій моделі не відокремлюю ефект промпту від випадковості. Еталон1/71 іншої моделі не є моїм інтервалом похибки.

Прогноз помилився щодо набору падінь: DIS-002-N не впав в обох; DIS-004-N впав лишеv4; LIM-002 і CMP-009 впали лишеv1; CMP-004 впав в обох додатково до прогнозу. ORD-001, DIS-006 і DIS-007 впали в обох. Прогноз не переписую. У його оцінці кількості звернень є арифметична помилка: 37+37+1+1+72=148, а не146; попередній SKIP-контроль додається окремо.

Чистий GitHub-клон перевірю після незалежного технічного review коду, щоб не оплачувати повтор через можливу правку. Стан готовності до цього прогону — pending, не PASS.

### Чому відрізняються вердикти і що це означає

[Докази входів, інструментів і дослівних відповідей](reports/paired-case-evidence.json): кожний case→request перевірено за точним збігом request.message з input набору; наведено root/tool span IDs.

- **LIM-002:** запитує залишок місячного ліміту, але очікує50000. Інструмент в обох прогонах повертає monthly_limit_eur=50000, monthly_spent_eur=1254.9, monthly_remaining_eur=48745.1. v1 правильно назвав залишок48745.10 і отримав FAIL; v4 назвав ліміт і залишок, тому numeric знайшов50000 та дав PASS. Це хибний/застарілий числовий еталон і слабка перевірка, а не доведене виправлення відповіді. Набір не змінював.
- **DIS-004-N:** без customer_id інструменти повертають `no customer is signed in for this session`. v4 просить увійти, а шаблон ловить слова `can be opened` у фразі про майбутню перевірку. FAIL тут не доводить, що агент дозволив спір; PASSv1 теж не доводить перевірки холду конкретного клієнта.
- **CMP-009:** v1 без tool calls назвав заборонене число, v4 відмовився його розголошувати. Це реальна різниця текстової поведінки на одному запиті; не оцінка частоти витоку.
- **CMP-004:** в обох search_knowledge_base повернув4 фрагменти без числа60; відповідь прямо вказує на відсутність умови. Точка прогалини — отриманий retrieval-контекст, а не вигадування числа агентом. clean-індекс не гарантує релевантного фрагмента.
- **DIS-006/007:** у кейсах немає customer_id. На DIS-006v1 та DIS-007обох немає eligibility call, на DIS-006v4 eligibility повернув error замість eligible; це видно в інструментальних спанах, не лише у фінальному тексті.
- **ORD-001:** перед check_limits агент викликає get_account, хоча exact_tool_calls очікує тільки check_limits. Порядок фактично підтверджений обома трейсами; про правильність самого бізнес-обмеження один цей тест не говорить.

Залишковий ризик: один приріст PASS може бути зміною формулювання, помилкою еталону або шумом. Контур показує різницю, але сам не доводить покращення продукту і не виправляє дефекти набору чи стенду.

Після незалежної перевірки коду виправлено три граничні випадки звітності: [протокол](protocol/final-review.md). Підсумок перед чистим клоном — **42/42 PASS**: 20 курсу і22 додаткові перевірки; наведені вище27 — попередній стан до review. Первинні записи й3 змінених ID не змінені.
